# 云起科技 CRM 接口自动化框架面试准备

## 这份笔记怎么用

这份专门讲我的接口自动化框架项目：

`E:\pytest_auto_api_my`

不要把它说成真正完整覆盖了 CRMEB 或 CRM 全业务。更准确的说法是：

> 我基于 `pytest + requests + yaml` 搭建了一个接口自动化框架，用 CRMEB 商城接口做练习场景，重点验证登录、商品、购物车、地址、下单等主流程。面试云起科技 CRM 岗位时，我会把这个框架能力迁移到 CRM 会员、优惠券、标签、短信触达、订单同步等接口测试场景里去讲。

## 项目一句话介绍

可以这样说：

> 这个项目是我自己搭建的接口自动化测试框架，技术栈是 `pytest + requests + yaml`。框架把接口数据写在 YAML 里，通过 pytest 参数化读取用例，统一发送 HTTP 请求，统一做状态码和业务字段断言，并支持把登录 token、商品 ID、购物车 ID、订单号这些字段提取到上下文，供后续接口复用。

更短版：

> 我做的是一个 YAML 数据驱动的接口自动化框架，核心能力是统一请求封装、统一断言、上下文参数传递和多接口业务流串联。

## 框架目录怎么讲

可以这样说：

> 我的框架按职责分了几层：`data` 放 YAML 用例数据，`test_case` 放 pytest 测试入口，`util` 放核心工具能力，`common` 放配置。`util` 里面又拆了请求封装、断言、提取、上下文和 YAML 读取。这样接口用例和代码逻辑分开，后续新增接口时主要维护 YAML，不需要在每个测试脚本里重复写请求和断言。

对应目录：

- `data/`：接口 YAML 用例。
- `test_case/`：pytest 测试入口。
- `util/requestsUtils/`：请求封装。
- `util/assertion/`：断言控制。
- `util/extract/`：响应字段提取。
- `util/context/`：上下文管理。
- `util/readFileUtils/`：YAML 读取、用例解析、占位符替换。
- `common/`：环境配置和路径配置。

## 执行流程怎么讲

面试说法：

> 整体流程是：先编写 YAML 用例，再由 pytest 读取用例并参数化执行；执行时会先解析公共参数和占位符，然后通过请求封装统一发送接口请求；响应返回后，先执行状态码和 JSONPath 断言，再按提取规则把关键字段保存到上下文，后续接口可以通过占位符继续引用这些值。

流程：

```text
编写 YAML 用例
    ↓
pytest 参数化读取
    ↓
合并公共参数
    ↓
替换上下文占位符
    ↓
统一发送 HTTP 请求
    ↓
执行状态码 / JSONPath 断言
    ↓
提取响应字段到上下文
    ↓
后续接口继续引用
```

## 高频面试题

### 1. 你这个接口自动化框架怎么设计的？

> 我的框架主要按职责拆分。YAML 负责维护接口数据；pytest 负责用例组织和参数化执行；请求封装层统一处理 host 拼接、headers、params、json、data 和请求发送；断言层统一做状态码和 JSONPath 业务断言；提取层负责从响应里提取 token、商品 ID、订单号等字段；上下文管理器负责保存这些字段，供后续接口通过占位符引用。这样测试代码会比较简洁，新增接口时主要维护 YAML。

### 2. 为什么要用 YAML 数据驱动？

> 因为接口测试里 URL、请求参数、断言字段和提取规则变化比较频繁，如果都写在代码里，维护成本会比较高。放到 YAML 里之后，测试数据和测试逻辑分离，新增或修改接口时主要改 YAML，测试代码相对稳定。公共 headers、公共参数也可以统一配置，减少重复。

### 3. 多接口依赖怎么处理？

> 我用上下文管理器处理接口依赖。比如登录接口返回 token 后，把 token 提取到上下文；商品接口返回商品 ID 后，也提取到上下文。后面的购物车、确认订单、创建订单接口，就可以通过占位符引用这些值。这样一条业务链路可以按接口执行顺序自动传递数据。

### 4. 你怎么保证用例之间不互相影响？

> 我会在 fixture 里控制上下文的初始化和清理。单接口用例和流程用例的上下文边界要分清楚：单接口用例执行前后可以清理上下文，流程用例则在一条链路内保留上下文，链路结束后再清理，避免 token、订单号这类数据污染其他用例。

### 5. 如果接口失败，你怎么定位？

> 我会先看失败发生在哪一步，是请求失败、状态码断言失败，还是业务字段断言失败。然后看请求 method、url、headers、params、body 是否正确，再看响应体里的业务码和错误信息。如果是链路用例，还会检查上游接口提取的变量是否正确，比如 token、商品 ID、订单号有没有取到。必要时再结合日志和 SQL 查库确认数据状态。

### 6. 断言怎么设计？

> 我一般分三层断言。第一层是 HTTP 状态码，比如是不是 200；第二层是业务码和返回结构，比如 code、message、data 是否符合预期；第三层是关键业务字段，比如订单号是否存在、商品数量是否正确、订单金额是否符合预期。只断言 HTTP 200 不够，因为很多接口 HTTP 成功但业务可能失败。

### 7. 提取规则怎么设计？

> 提取主要服务于接口关联。比如登录提取 token，商品列表提取商品 ID，购物车接口提取购物车 ID，下单接口提取订单号。提取后统一放到上下文里，后面的 YAML 用例通过占位符引用。这样可以把接口从单点测试串成完整业务流程。

### 8. 你这个框架和 Apifox 的关系是什么？

> Apifox 更适合前期接口调试、联调和链路验证。我通常会先在 Apifox 里把接口参数、响应结构、变量关联和断言思路调通；等接口稳定后，再把它沉淀成 YAML 自动化用例，放到 pytest 框架里做回归测试。两者不是替代关系，而是前期调试和后期自动化沉淀的关系。

### 9. SQL 在这个项目里怎么用？

> 当前框架主要做接口层断言，SQL 校验可以作为增强方向。实际接口测试里，我会在关键业务场景结合 SQL，比如下单后查订单主表和订单明细表，支付后查支付状态，优惠券领取后查库存和用户领券记录。这样能确认接口返回、页面展示和数据库结果是否一致。

### 10. 这个框架还有什么不足？

> 目前框架已经具备用例数据分离、请求封装、统一断言、字段提取和上下文传递，适合做主流程接口回归。后续我会继续增强数据库断言、测试数据自动清理、失败重试、日志和报告展示、多环境配置校验，以及把 Apifox 调通的接口更方便地转换成 YAML 用例。

## 和云起科技 CRM 岗位怎么结合

可以这样说：

> 虽然我这个框架练习时用的是商城接口，但能力可以迁移到 CRM 系统。CRM 里常见的会员登录、会员查询、优惠券发放、标签更新、短信触达、订单同步、活动效果查询，都可以维护成 YAML 用例。比如优惠券发放链路，可以先登录获取 token，再创建或查询会员，调用优惠券发放接口，最后查询用户券记录和库存变化。框架负责把这些接口串起来，并做状态码、业务字段和关键结果断言。

## CRM 接口测试可以重点讲哪些业务

### 会员接口

- 会员注册 / 登录。
- 会员资料查询和修改。
- 会员等级、积分、余额。
- 会员状态是否正常。

### 优惠券接口

- 正常领取。
- 重复领取。
- 库存不足。
- 已过期 / 未开始。
- 会员等级限制。
- 指定人群限制。
- 多人同时领取是否超发。

### 标签和人群接口

- 标签新增、修改、删除。
- 用户打标签是否准确。
- 标签覆盖还是追加。
- 人群筛选结果是否符合规则。

### 短信触达接口

- 短信任务创建。
- 发送对象是否正确。
- 发送状态是否更新。
- 失败是否重试。
- 发送记录是否落库。

### 订单同步接口

- 订单是否同步成功。
- 订单状态是否一致。
- 金额、优惠、支付状态是否正确。
- 重复同步是否幂等。

## 项目亮点

- YAML 数据驱动，测试数据和测试代码分离。
- pytest 参数化执行，方便批量跑接口用例。
- requests 二次封装，统一处理请求发送。
- 上下文机制支持多接口业务流串联。
- 支持从响应里提取 token、商品 ID、订单号等变量。
- 支持状态码和 JSONPath 业务字段断言。
- 目录分层清晰，后续新增接口主要维护 YAML。
