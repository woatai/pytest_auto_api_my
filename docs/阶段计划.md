# 阶段计划（框架升级路线图）

> 更新时间：2026-04-13
>
> 这份计划基于当前仓库真实状态重新整理，已删除早期“已完成或已过时”的阶段目标，保留后续最值得投入的升级路径。

---

## 一、当前状态判断

### 已有基础能力
- 已具备 `RequestControl`、`AssertControl`、`ExtractControl`、`ContextManager` 这四个核心组件。
- 已具备 YAML 读取、`case_common` 合并、基础占位符替换、JSONPath 提取、统一断言。
- 已具备下单主流程样例：`login -> product_list -> product_detail -> default_price -> user_center -> buy_now -> check_shipping -> get_default_address -> order_confirm`。
- 已有基础单测，能覆盖请求封装、占位符、断言、提取等核心能力。
- 已能生成 Allure 报告，具备初步演示能力。

### 当前主要问题
- 流程测试仍以手写步骤为主，重复代码较多，尚未沉淀成通用流程执行器。
- 请求失败时虽然保留了调试信息，但错误暴露还不够聚焦，真实网络异常容易被“状态码为 None”掩盖。
- 上下文变量依赖执行顺序，缺少更稳定的初始化、清理和依赖管理机制。
- YAML 结构目前偏自由，缺少字段校验、跳过策略、优先级、重试、前后置等工程化能力。
- 真实接口联调容易受环境影响，缺少 mock / 回放 / 离线验证能力。

### 升级原则
- 先补地基，再扩功能。
- 先做“高频使用、直接提效”的能力，再做“大而全”的平台能力。
- 不直接照搬外部开源框架，优先保留当前仓库清晰、轻量、易理解的结构。

---

## 二、已完成项归档

以下能力已经具备，不再作为当前阶段待办：
- 请求基础封装：相对路径与完整 URL 兼容。
- 基础断言封装：`status_code`、JSONPath 断言、失败信息输出。
- 基础提取封装：普通 JSONPath 提取、条件提取。
- 基础上下文传值：测试步骤间变量共享。
- 基础占位符能力：`${{host()}}`、`${{token}}`、`${{product_id}}` 等。
- 下单主流程样例 YAML 与测试骨架。
- Allure 报告生成链路。

## 三、阶段路线图

## 阶段 P0：基线治理与可执行性加固  done

### 目标
把框架从“能跑部分场景”提升到“测试能被发现、失败能被定位、流程能稳定复现”。

### 任务
- 修复测试发现问题。
  - 统一测试文件、测试类、测试方法命名。
  - 确保 `pytest --collect-only -q` 能正确收集所有目标用例。
- 增加统一的 `conftest.py` 基础设施。
  - 在每条流程开始前清理 `ContextManager`。
  - 为登录初始化、环境切换、公共前置预留 fixture。
- 强化请求异常暴露。
  - 请求失败时在断言报错中明确输出异常文本、请求 URL、请求头、请求体。
  - 增加耗时、重试次数、超时值等调试信息。
- 拆掉流程测试中的重复代码。
  - 抽出统一的步骤执行函数。
  - 让 `test_order_main_flow.py` 只保留流程编排，不重复写相同的发送请求和断言逻辑。
- 增加联调保护开关。
  - 支持“真实环境模式”和“离线/Mock 模式”切换。
  - 保证无网络或目标服务异常时，核心框架能力仍可验证。

### 验收标准
- `pytest --collect-only -q` 能看到所有预期测试。
- `pytest test_case/test_framework_basics.py -q` 稳定通过。
- 主流程失败时，日志或断言信息能直接定位是“网络失败 / 占位符缺失 / 断言失败 / 提取失败”中的哪一类。
- `test_order_main_flow.py` 中重复代码明显下降，步骤执行逻辑统一。--已完成

## 阶段 P1：YAML DSL 与流程执行器升级

### 目标
把当前“样例级 YAML”升级为“可复用、可维护的流程 DSL”。

### 任务
- 引入 YAML 字段校验。
  - 校验 `url`、`method`、`assert`、`extract` 等关键字段。
  - 对缺失字段、非法类型、非法断言格式给出明确报错。
- 升级通用流程执行器。
  - 支持按步骤顺序自动执行。
  - 支持单步运行、指定 case_id 运行、失败即中断。
  - 支持从 YAML 直接生成流程，不依赖大量手写测试函数。
- 增加流程控制字段。
  - `name`
  - `is_run`
  - `tags`
  - `priority`
  - `timeout`
  - `retry`
  - `depends_on`
- 完善 `case_common` 机制。
  - 支持公共请求头、公共鉴权、公共标签、公共超时。
  - 评估是否需要从浅合并升级为可控的深合并。

### 验收标准
- YAML 配错时，能在执行前报出结构问题，而不是运行中才报错。
- 主流程可通过统一执行器运行，新增流程时不必复制大量测试代码。
- 新增一条流程时，重点工作变成“写 YAML”，而不是“重复造测试函数”。

---

## 阶段 P2：占位符、提取和断言能力增强

### 目标
把框架从“可跑主流程”升级到“能覆盖更多接口场景”。

### 任务
- 增强占位符引擎。
  - `${{timestamp()}}`
  - `${{uuid()}}`
  - `${{random_int(1,100)}}`
  - `${{random_str(8)}}`
  - `${{faker.name()}}`
  - `${{faker.phone_number()}}`
- 增强提取能力。
  - 支持 `required`、默认值、批量提取、列表选择、条件提取优化。
  - 支持从响应头、响应体、请求体中提取数据。
- 增强断言能力。
  - `eq / ne / gt / ge / lt / le`
  - `contains / in / regex`
  - `exists / not_exists`
  - 长度断言、类型断言
- 优化上下文变量管理。
  - 明确作用域：单用例、单流程、全局会话。
  - 支持上下文快照输出，方便排查变量污染。

### 验收标准
- 常见动态数据场景不需要手工在测试代码里拼值。
- 断言类型足够覆盖大多数接口验证场景。
- 提取失败和变量污染问题可快速定位。

---

## 阶段 P3：工程化能力补齐

### 目标
让框架具备团队协作、持续集成和长期维护能力。

### 任务
- 日志体系升级。
  - 区分 `INFO / WARNING / ERROR`。
  - 输出请求摘要与完整调试信息。
  - 对 `password`、`token`、`Authorization` 做脱敏。
- Allure 报告增强。
  - 附加请求 URL、请求头、请求参数、响应体。
  - 附加提取变量和上下文快照。
  - 附加失败原因分类。
- 环境与配置治理。
  - 支持 `dev / test / prod` 多环境。
  - 账号、密码、Token 等从 YAML 中剥离。
  - 逐步引入 `.env` 或独立密钥配置。
- 运行入口治理。
  - 改造 `run.py`，支持指定环境、指定模块、指定标签、是否生成报告。
  - 标准化报告目录与历史结果清理策略。
- CI 能力预埋。
  - 为后续接入 Jenkins / GitHub Actions / GitLab CI 预留命令入口。

### 验收标准
- 失败后不需要二次加打印就能定位问题。
- 敏感信息不会直接出现在日志和报告中。
- 本地运行和 CI 运行使用同一套入口参数。

## 阶段 P4：高级能力扩展

### 目标
把框架升级为真正可持续扩展的接口自动化平台雏形。

### 任务
- 前后置能力。
  - `setup`
  - `teardown`
  - 数据清理策略
- 数据源能力。
  - SQL 断言
  - SQL 前置准备
  - Redis / 缓存断言
- 请求类型扩展。
  - 文件上传
  - 文件下载
  - 表单请求
  - 自定义 Content-Type
- 用例生成提效。
  - OpenAPI / Swagger 转 YAML
  - 用例模板生成器
  - 录制回放能力
- 通知与统计。
  - 钉钉 / 飞书 / 企业微信通知
  - 执行趋势、失败分类统计

### 验收标准
- 新业务接入不只是“能写”，而是“写得快、查得清、回归稳”。
- 框架具备从个人项目走向团队项目的能力基础。

## 六、产出目标

完成本轮升级后，项目应达到以下效果：

## 七、补充说明

- 当前阶段不追求一次性做成“大而全”的企业平台。
- 当前最重要的目标，是把“可执行性、可维护性、可定位性”三件事做稳。
- 后续新增能力应优先做成可插拔模块，避免把请求、断言、提取、日志、通知全部堆进一个超大控制器。
