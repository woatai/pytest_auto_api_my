# 从零开始搭建接口自动化框架

> 面向零基础：先搞懂「要做什么」和「先做哪一步」，再动手写代码。

---

## 第一步：先搞清楚「接口自动化」在做什么

**接口自动化** = 用程序代替人工，反复、稳定地调用接口并检查结果是否正确。

- **调用接口**：发 HTTP 请求（GET/POST 等），带上 URL、参数、请求头。
- **检查结果**：看状态码、响应体里的字段（如 `code`、`data`）是否符合预期。

所以框架要解决两件事：

1. **怎么发请求** → 需要「请求封装」。
2. **怎么判断对错** → 需要「断言」。
3. **怎么组织很多用例** → 需要「用例管理」（目录 + 数据/代码）。
4. **怎么一键跑全部** → 需要「运行入口」+ 测试框架（如 pytest）。

下面按「从哪开始、先做啥、后做啥」的顺序讲。

---

## 第二步：从哪里开始？—— 建议顺序

整体顺序可以理解为：

```
1. 建好项目目录（知道代码放哪）
2. 能发一条 HTTP 请求（请求封装）
3. 能对响应做断言（断言）
4. 用 pytest 跑一条用例（运行链路打通）
5. 把用例数据放到 YAML（数据与代码分离）
6. 加配置（环境、host）
7. 加日志、报告等（增强）
```

**真正动手的起点**：先建目录，再写「发一条请求 + 断言」，最后用 pytest 跑起来。  
其他（YAML、配置、日志）都是在这条链路打通之后再往上加。

---

## 第三步：项目目录先画出来

先定好「东西放哪」，后面不会乱。最小可运行结构可以是这样：

```
pytest_auto_api/
├── common/           # 配置（后面再加）
├── data/             # 用例数据 YAML（第 5 步用）
├── test_case/        # 测试用例代码（pytest 从这里找用例）
├── utils/            # 工具：发请求、断言、读配置等
├── run.py            # 运行入口：执行 pytest
├── pytest.ini        # pytest 配置
└── requirements.txt  # 依赖
```

**你现在要做的**：在本地建好这些文件夹和文件（空的也行），心里有数「请求封装会放 utils，用例会放 test_case」。

---

## 第四步：先打通「发请求」—— 请求封装

目标：**写一个函数，传入 URL、方法、参数，就能发 HTTP 请求并返回结果。**

- 用 Python 的 `requests` 库发请求。
- 函数返回「状态码 + 响应体」，方便后面断言。

**放在哪**：`utils/requestsUtils/requestControl.py`（或你喜欢的路径）。

**要实现的函数大致长这样**：

```python
# 伪代码理解
def request_control(method, url, headers=None, params=None, data=None):
    resp = requests.request(method=method, url=url, headers=headers, params=params, json=data, ...)
    return {"status_code": resp.status_code, "body": resp.json()}
```

**验证方式**：在项目里写一个临时脚本或单独 test，调用这个函数请求 httpbin.org/get，能打印出 200 和响应体，就说明「发请求」这一步通了。

---

## 第五步：再打通「断言」

目标：**根据「期望值」和「实际值」判断用例通过还是失败。**

- 实际值：来自上一步的 `status_code`、`body`。
- 期望值：可以是写死在代码里，或之后从 YAML 里读。

**放在哪**：`utils/assertion/assert_control.py`。

**要实现的逻辑**：

- 比较状态码：`assert resp["status_code"] == 200`。
- 比较 body 里某个字段：先用 jsonpath 或字典取到值，再 `assert 实际 == 期望`。

断言失败时用 `assert` 抛错，pytest 会认为用例失败并标红。

---

## 第六步：用 pytest 跑通「一条用例」

目标：**一条用例 = 发一次请求 + 做一次断言，用 pytest 执行。**

- 在 `test_case/` 下新建 `test_xxx.py`，里写一个 `test_xxx()` 函数。
- 在函数里：调用你的「请求封装」发请求，再用你的「断言」检查结果。
- 在项目根目录执行：`pytest test_case/test_xxx.py -v`，能看到这条用例通过或失败。

**到这里**：你已经有了「最小框架」—— 能发请求、能断言、能用 pytest 跑。  
后面都是在这条链路上加：更多用例、YAML、配置、日志、报告。

---

## 第七步：加配置（环境、host）

目标：**把「环境地址」从代码里抽出来，改环境只改配置。**

- 在 `common/` 里放 `conf.yaml`（写 test/prod 的 host）和 `setting.py`（项目根路径等）。
- 请求封装里用「当前环境的 host + 接口路径」拼成完整 URL。

这样换环境只改 `conf.yaml`，不用改用例代码。

---

## 第八步：用例数据放 YAML（数据驱动）

目标：**接口地址、参数、断言期望都写在 YAML 里，代码只负责「读 YAML → 发请求 → 断言」。**

- 在 `data/` 下为每个业务建 yaml（如 `login.yaml`、`order.yaml`）。
- 在 `utils/readFilesUtils/` 里写「读 yaml + 解析成用例列表」的函数。
- 用例里：用解析结果里的 url、method、data、assert 去调「请求封装」和「断言」。

这样以后加新场景，主要是加/改 YAML，代码改动很少。

---

## 第九步：增强功能（按需加）

- **日志**：在请求前后、断言失败时打 log，方便排查。
- **报告**：用 allure 或 pytest-html 生成报告。
- **依赖**：比如先登录拿到 token，再在后续请求里带 token → 用「缓存」存 token，请求里用占位符替换。
- **通知**：跑完发钉钉/企微（可选）。

这些都是在「请求 + 断言 + pytest + 配置 + YAML」之上叠加，不会改变「从哪里开始」的顺序。

---

## 总结：你先做哪几件事（清单）

| 顺序 | 要做的事 | 验证方式 |
|------|----------|----------|
| 1 | 建好项目目录（common/data/test_case/utils + run.py、pytest.ini、requirements.txt） | 能列出这些文件夹 |
| 2 | 写「请求封装」函数，能发 GET/POST | 脚本调一次，能拿到 200 和 body |
| 3 | 写「断言」逻辑，比较 status_code 和 body 字段 | 写个 test 调请求+断言，pytest 能跑过 |
| 4 | 在 test_case 里写一条完整用例（请求+断言） | `pytest test_case/ -v` 通过 |
| 5 | 加 common 配置，请求里用配置的 host | 改 conf 里 host，再跑用例验证 |
| 6 | 加 YAML 用例数据 + 读 YAML 的代码 | 用例从 yaml 读数据再请求/断言 |

**真正的起点**：第 1 步建目录 + 第 2 步请求封装。这两步做完，再按 3 → 4 → 5 → 6 往下走，你就不会迷路。

你当前项目里已经按这个思路搭好了，你可以对照上面的步骤，打开对应文件（如 `requestControl.py`、`assert_control.py`、`test_order_main_flow.py`）逐行看，理解「这一步对应的是哪一环节」。有哪一步想深入（比如「请求封装怎么写更稳」「YAML 怎么设计」），可以指定步骤号或文件名，我可以按那一步展开讲或改一版示例代码给你练手。
